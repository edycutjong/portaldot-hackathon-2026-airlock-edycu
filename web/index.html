Questions a judge would ask.

Short answers, each one checkable in the repository.

Is this on a real chain?
Yes. The core flow ran on the Portaldot V3 testnet (portaldot-v3/3002) on 2026-10-19 and again on 2026-10-24, and every V3 row in PROOF.md is re-fetched by extrinsic id (44/44). The benchmark ran only on labelled interim chains, not V3.
Did you deploy a contract or change the runtime?
No. Everything is enforced by the chain's own Proxy pallet; Airlock adds no custom runtime code. The vault is a pure proxy, the hot key is a proxy with a delay, the cold key a proxy with delay 0.
What can a stolen hot key do on its own?
Announce a call hash and wait. In the 2026-10-24 run, executing the sweep after the veto failed with Proxy.Unannounced (166825-1), and so did calling the proxy directly (166831-1).
What if the watcher is offline?
The delay is still enforced by the chain; nobody is alerted. After a restart the watcher catches up on the blocks it missed. That was recorded on the interim chains, not V3, after a watcher restart, a node restart and a node freeze (docs/WATCHER.md). The veto still has to land before the deadline block.
What is mocked?
The Telegram sender is built and tested against a mock Bot API; no alert has reached a phone yet. The benchmark's vetoes are automated. The thief is our own script (scripts/thief.py, no Airlock imports) holding the vault's hot key; its calls are real V3 extrinsics. The 2026-10-19 V3 rows are listed by id in PROOF.md, the 2026-10-24 run in its run record.
Why not a multisig?
A multisig needs a second signer for every payment, which is heavy for one person. Here a legitimate payment is the same flow with no veto: the cold key only acts when something is wrong.
